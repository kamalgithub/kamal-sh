# Design tokens

> Update this file when a token is added/changed/removed — not when a component merely uses one.

All tokens live in `src/lib/styles/tokens.css` as CSS custom properties, and are mapped into Tailwind v4 utility classes via an `@theme` block in the same file (Tailwind v4 is CSS-first — there is no `tailwind.config.js`). Components consume tokens through Tailwind classes (`bg-surface`, `text-accent`, `font-display`) or, where Tailwind has no matching utility, directly via `var(--token-name)`. **Never hardcode a hex value, font name, or timing value in a component** — add or reuse a token instead.

**Direction: Modern Editorial** (revised 2026-09-05, replacing the original glassmorphism/gradient skeleton — see git history for what came before and why it changed). A serif display face, a single flat accent used only as text/rules, and hairline-divided lists/dividers as the primary structural device instead of a grid of identical rounded, shadowed cards. This directly avoids the generic AI-design tells documented at the bottom of this file.

## Color

Dark is the default; light is a fully equal mode, not an afterthought (`prefers-color-scheme`, with a manual override via `ThemeToggle.svelte` — `src/lib/components/nav/ThemeToggle.svelte`, persisted through `src/lib/utils/theme.ts`, applied before first paint by the inline script in `app.html` so there's no flash of the wrong theme). All neutrals are true gray (`R=G=B`) — no warm cast, deliberately.

| Token                   | Dark      | Light     | Use                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------- | --------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--color-bg`            | `#0A0A0A` | `#FAFAFA` | page background                                                                                                                                                                                                                                                                                                                                                                         |
| `--color-surface`       | `#131313` | `#FFFFFF` | the few genuinely raised panels (contact form, booking widget) — not used for general content                                                                                                                                                                                                                                                                                           |

| `--color-border-strong` | `#606060` | `#868686` | functional boundaries — `Card`, form inputs, booking picker buttons — anywhere the border is the only cue that a control exists. | `--color-error`         | `#F87171` | `#DC2626` | form validation feedback — the only other functional color. Both accent values verified against their background via the WCAG relative-luminance formula: dark `#5C82FF` on `#0A0A0A` is ~5.75:1, light `#2544B0` on `#FAFAFA` is ~8.14:1 — both comfortably clear AA (4.5:1) for normal text, which matters because accent is used as **text**. As a **button fill** it's verified separately (the foreground isn't the same background it's used as text against) — see the primary-button note under "Surfaces & structure" below.

Rule: `--color-accent` and `--color-error` are the only colors carrying functional _meaning_ (state/validation). `--color-border-strong` is a contrast tier of the existing border color, not a new meaning — use it, don't invent a third border token. Keep the palette minimal; every token here exists because of a verified, unavoidable need, not a stylistic want.

## Surfaces & structure

There is no glass/blur/gradient system anymore, and no grid-of-identical-rounded-cards pattern. Both are the single most common tell of generic AI-generated design (content chopped into identical rounded cards, the same soft shadow under each, gradient washes as decoration) — see the "Avoiding generic tells" section below.

- **Hairline dividers are the primary structural device.** Most content lists (testimonials, products, case studies, certifications, education, experience, writing) are `<ul class="divide-y divide-border border-t border-border">` — a top rule plus a rule between each item. No box, no shadow, no per-item border-radius. These use `border-border` (the soft, decorative token) — never `border-border-strong`, which is reserved for functional boundaries.
- **`Card.svelte`** (flat `bg-surface` + `border-border-strong`, small `rounded-sm`, no blur) is reserved for genuinely raised functional UI — currently the contact form, booking widget, and the architecture-diagram detail panel. It is not the default wrapper for arbitrary content. Form inputs and the booking picker's date/duration/time buttons also use `border-border-strong` for the same reason: the border is the only cue those controls exist.
- **Radius convention:** small and consistent (`rounded-sm` on buttons, inputs, `Card`) — never a full pill on a CTA button (reads as generic "SaaS app," not editorial), never zero-radius everywhere either (that's its own generic tell — see below). Small icon-only utility buttons (nav hamburger/close) are the one exception that stays `rounded-full`, since a circular icon button isn't the pattern being avoided.
- **`Button.svelte` primary variant** is a solid accent fill: `bg-accent text-bg`. It was originally a monochrome "ink stamp" (`bg-text text-bg`) specifically to _avoid_ verifying a second contrast pair — revised after direct feedback that an all-black/all-white button read as broken/colorless. `--color-bg` turns out to be exactly the right text color for this: dark mode's accent needs near-black text (`--color-bg` dark is `#0A0A0A`, ~5.7:1) and light mode's accent needs near-white text (`--color-bg` light is `#FAFAFA`, ~7.9:1) — the same token that already flips between those two values for the page background happens to flip the right way for button text too, so no new token was needed. Secondary stays an outline in the ink color (`border-text`), unchanged. If a new accent shade is ever chosen, re-verify both of these ratios — they depend on the specific hex values, not just "accent contrasts with itself."

**Per-page hero tint:** `Section.svelte` takes an optional `tint?: 1 | 2 | 3` prop (`bg-tint-1`/`2`/`3`, plus a `border-b border-border` hairline closing off the tinted band). Only a page's opening `<Section>` should pass it — every other `Section` on that page stays untinted. This was a deliberate, scaled-down answer to "should each page look different": a full per-page hero treatment (distinct imagery/gradients per route) was rejected as too close to a marketing-site feel for a content-first site; three barely-perceptible lightness steps between `--color-bg` and `--color-surface` (no hue shift, keeping the "no warm cast" rule above) give each top-level page a faint identity without it reading as an intentional color choice. The hairline underneath is the same `border-border` hairline used everywhere else on the site as a divider — it gives the tint band a crisp edge instead of a soft fade, and reads as "hero section ends here" independent of whether the tint itself is even noticeable. Assigned by hand per page (not derived from data — this is a styling choice, not content), verified 2026-09-09 against every route's actual `tint={...}`: `1` — Work, Writing, Testimonials, Postmortems, Changelog, Newsletter, Now; `2` — Architecture, About, Security, Uses; `3` — Building, Contact, Costs, Status. Untinted: Home (the baseline everything else is a subtle step away from), the `/work/[slug]` and `/building/[slug]` detail pages, and `/resume-print` (a print-first page — a decorative tint band has no reason to exist there).

## Images

`Figure.svelte` (`src/lib/components/primitives/Figure.svelte`) is the one component that renders an image: it takes an optional `image: ContentImage` (`src/lib/content/image.types.ts` — `{ src, alt, darkSrc? }`, shared by `Profile.photo`, `CaseStudy.image`, and `Product.image` so the shape is defined once) plus a required `width`/`height`/`label`. When `image` is present it renders a real `<img>` sized to prevent layout shift; when it's absent (no real asset exists yet) it renders a tokenized, dashed-border placeholder box at the same aspect ratio, with an icon and `label` explaining what belongs there. This is the standard way this site handles "we don't have the real asset yet" — never a broken `<img>`, never a layout gap. Leaving `image` itself `undefined` is a valid, fully-supported state, not a TODO to silence a type error.

An optional `class` prop overrides the default `h-auto w-full rounded-sm border border-border object-cover` sizing/border classes on the rendered `<img>`(s) only — the placeholder branch is unaffected. Added for `Hero.svelte`'s portrait: the default hairline `border-border` is ~1.3:1 contrast, deliberately subtle for a case-study/product image sitting on a page's normal background — but the portrait photo has its own near-black background that's nearly identical to `--color-bg` in dark mode, so that hairline was effectively invisible and the photo read as an ill-defined floating block rather than a framed portrait. The fix wraps `Figure` in its own `border-border-strong` + `bg-surface` + padding container (a visible "matte" frame, like a printed photo's mount) and passes `class` to drop `Figure`'s own border so it isn't doubled — this gives the portrait a clear, theme-independent boundary regardless of what color the photo's own background happens to be.

**Dark/light image variants:** when `image.darkSrc` is set, `Figure` renders _both_ `<img>`s (classed `theme-image-light` / `theme-image-dark`) and `src/lib/styles/theme-image.css` shows exactly one via the same dark-default/`prefers-color-scheme`/`[data-theme]` override logic `tokens.css` uses for colors — pure CSS, no flicker, works on a fully prerendered page. `darkSrc` is optional on purpose: most images (a photo, an external blog thumbnail) don't need a separate version — only add one where the image itself is visibly theme-specific, like a diagram drawn against a particular background.

## Typography

Self-hosted, real files (not system-font fallback) — `static/fonts/`, `@font-face` rules in `src/lib/styles/fonts.css`:

- `--font-display: 'Fraunces', ui-serif, Georgia, 'Times New Roman', serif` — a modern soft-serif with real character, used for every heading. Serif is what signals "editorial" against a field of sans-only tech sites. One variable file (`Fraunces-Variable.woff2`, weight range 400-700, normal style only — no italic, since italic emphasis on headline words is itself a generic tell, see below). SIL OFL licensed via Google Fonts, free to self-host.
- `--font-body: 'Switzer', ui-sans-serif, system-ui, sans-serif` — body/UI text, five static weight files (300/400/500/600/700). Free to self-host per Fontshare's license. `tokens.css`'s dark block sets `font-weight: 300` as the inherited default (both light-mode blocks explicitly reset it to `400`) — Switzer's Regular (400) read as too heavy specifically in dark mode, particularly on Windows (see the font-smoothing note below for why that fix alone wasn't enough). Because `font-weight` inherits and Tailwind's `font-medium`/`font-semibold`/`font-bold` utilities are more specific, this only affects text that doesn't already set its own weight (paragraphs, labels, muted nav text) — every heading and anything using those utilities is unaffected. **This is dark-mode-only, on purpose** — light mode never had this problem, and applying it there made body text too thin against a light background.
- Fluid type scale via `clamp()`, defined in `tokens.css`: `--text-display`, `--text-h1`, `--text-h2`, `--text-body`, `--text-small` — scale between a mobile-sane minimum and a desktop maximum, no fixed `px` sizes for typography outside this scale. `--text-display` uses a tight `line-height: 1` to suit the serif's large-scale proportions.
- `--font-mono: ui-monospace, SFMono-Regular, Menlo, Consolas, 'Liberation Mono', monospace` — native stack, no self-hosted file. Used sparingly for CLI-flavored moments (the "$" logo prefix, the command palette's input and keyboard hints) — never for body copy.

**Preloaded above the fold:** `app.html` preloads `Fraunces-Variable.woff2` and `Switzer-Light.woff2` (the dark-mode default weight, 300 — see above) with `<link rel="preload" ... crossorigin>`, so both arrive before `font-display: swap` would otherwise discover them via CSS. `crossorigin` is required even though these are same-origin — the browser silently ignores a font preload without it. If the font set changes (a new face, a different default weight), update these two preloads to match; don't preload every weight, only what's genuinely visible on first paint.

**Dark-mode font smoothing:** `tokens.css`'s dark block sets `-webkit-font-smoothing: antialiased` / `-moz-osx-font-smoothing: grayscale`; the light overrides reset both to `auto`. Light text on a dark background reads visually heavier than the same weight on light — a real rendering/perception effect, not something to fix by swapping to a different font weight on its own. Light mode doesn't have this problem, hence the reset rather than applying it everywhere. Worth knowing: this property is largely a WebKit/macOS thing and does little on Windows — it's a real but partial fix. The bigger, cross-platform fix for "text feels too bold" was lowering the actual default weight (`--font-body` above), not this.

## Icons

Hand-authored inline SVG components in `src/lib/components/icons/` (`IconArrowRight.svelte`, `IconShield.svelte`, etc.) — a 20×20 viewBox, `stroke="currentColor"`, `stroke-width="1.5"`, round caps/joins, matching the style the nav's menu/close icons established before this set existed. Each takes one optional `size` prop (default `20`). No icon library dependency: this repo's icon needs are a fixed, small set (~15), and hand-authoring them keeps the bundle native and avoids a whole package for a handful of glyphs — see the native-first policy in `docs/tooling.md`. Only generic, non-brand glyphs are drawn this way; social platform links use a plain external-link arrow (`IconArrowUpRight`) next to the text label instead of a reproduced brand logo.

**Where icons carry real weight vs. where they stay quiet:** most icon usage on this site is deliberately small and secondary (14–18px, muted color) — a hint next to a link, not a focal point. A few places are the exception, chosen because the icon does real informational work, not decoration:

- The architecture diagram's nodes each carry an icon tied to their `ArchitectureNode.icon` key (`layers`/`shield`/`gauge`/`checkCircle`/`activity` — see `src/lib/content/architecture.types.ts`), reused across nodes on purpose so a reader can visually group, say, every protective boundary at a glance.
- The stats band (`StatsBand.svelte`) and the GitHub activity feed (`GithubActivity.svelte`) both key an icon off a string field on the data itself (`Stat.icon`, `GithubActivityItem.icon`) rather than a fixed icon per component — the point in both cases is that _which_ icon shows changes per item (followers vs. subscribers vs. years; a push vs. a new branch vs. a pull request), so the icon is carrying information, not just decorating a static heading.
- `PageHeading.svelte` sets a single icon mark _above_ the `<h1>` (never beside it — it would compete with `--text-display`'s scale) on **every page's opening heading except Home**. This used to be reserved for the secondary/meta pages (architecture, security, costs, postmortems) only, on the theory that the serif headline alone carries identity on the core narrative pages — revised after direct feedback that the site wanted this treatment everywhere, for visual consistency across pages. Home is the one deliberate holdout: its hero is `Hero.svelte`'s own two-column layout with the profile photo as the visual anchor, and a small icon mark stacked above the tagline there would compete with the photo rather than complement it, the same reasoning that originally scoped this pattern down. If Home's hero layout ever changes to drop the photo, revisit whether it should pick up a `PageHeading` too.
- Testimonial cards (`TestimonialsGrid.svelte`) use a large, low-opacity `IconQuote` as a purely decorative corner mark (`text-border-strong/50`, `aria-hidden`, `pointer-events-none`) — the one place an icon is allowed to be bigger than the small-and-quiet default, specifically because it's inert decoration next to real content, not a competing focal point.

## Motion

| Token             | Value                                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------ |
| `--ease-standard` | `cubic-bezier(0.22, 1, 0.36, 1)` — cheap spring-like ease-out, no JS physics engine needed |
| `--duration-fast` | `120ms`                                                                                    |
| `--duration-base` | `200ms`                                                                                    |

**Hard rule** (see CLAUDE.md): never animate `transform: scale()` or a position offset on an interactive element, on hover or otherwise. Animate `opacity`, `background-color`, `border-color`, `color`, or `text-decoration-color` only — an element's size and position must never change on interaction, so click targets stay exactly where the user expects them.

**Scroll-entrance motion:** `src/lib/utils/reveal.ts` is a Svelte action (`use:reveal`) that fades and lifts an element 8px into place the first time it crosses into the viewport, using a plain `IntersectionObserver` — no library. It's applied once, at the root, on `Section.svelte`'s `<section>` element, so every section-level block across the site gets the same subtle entrance treatment for free; individual components don't need to add it themselves. It's a one-shot _entrance_ animation triggered by scroll position, not a hover/focus interaction, so it doesn't conflict with the no-scale/no-shift rule above. It no-ops entirely under `prefers-reduced-motion: reduce`.

**Gotcha:** `--ease-standard` correctly generates an `ease-standard` Tailwind utility (Tailwind v4's `--ease-*` namespace does a keyed theme lookup). `--duration-*` does **not** work the same way — Tailwind's `duration-*` utility parses its suffix as a raw number, so a named key like `duration-fast` silently compiles to nothing (no error, no CSS rule — verified against the real Tailwind v4 CLI output before this was trusted). Use the canonical CSS-variable syntax instead: `duration-(--duration-fast)`, which correctly compiles to `transition-duration: var(--duration-fast)`.

## Avoiding generic AI-design tells

Kept here because it's exactly the kind of non-obvious constraint a future agent (human or AI) could easily undo by accident while "improving" a page. Calibration for what generic AI-generated design clusters around, and what this site deliberately avoids:

- **The SaaS-card kit** — content chopped into identical rounded cards, one border-radius on everything, the same soft grey shadow under each, gradient washes as decoration. This was the original design direction here and got replaced specifically because of this. See "Surfaces & structure" above.
- **A warm cream background with a high-contrast serif and a terracotta accent**, or **a near-black background with a single bright acid accent used as the only distinctive move** — this site uses a serif display face and a near-black default, but the palette stays a true neutral (never warm) and the accent is deliberately restrained (flat, never a glow or gradient) so type and structure still carry most of the design, even now that the accent also fills the primary button.
- **A broadsheet layout with hairline rules and zero border-radius everywhere** — this site does use hairline rules extensively, but radius isn't zero across the board (see the radius convention above) — full commitment to zero-radius is its own recognizable tell.
- **Template chrome**: tracked-out ALL-CAPS eyebrow labels above headings, meta strings joined with middle dots (`A · B · C`), labels built as `WORD — fragment` with a spaced em dash, a `→` appended to link/button text. None of these appear anywhere in this codebase's copy — if you're adding a new piece of UI copy, don't reach for any of them. Prefer plain grammatical joins ("Name, Role" not "Name · Role"; "2022 to 2024" not "2022 — 2024").
- **Italicizing/coloring a single word in a headline for emphasis** — don't. If a headline needs emphasis, the whole headline's weight/size does the work.
