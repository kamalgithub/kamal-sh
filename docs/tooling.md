# Tooling

> Update this file when you change how a tool is configured or used — not when you just use it normally.

## Stack

- **SvelteKit 2 / Svelte 5** — runes mode is forced project-wide via `vite.config.ts`'s `compilerOptions.runes`. Always write components with runes (`$state`, `$derived`, `$props`, `$effect`), never the Svelte 4 reactive-statement style.
- **A `+page.server.ts`'s `actions` export can't mix a `default` action with named ones.** SvelteKit throws a 500 at request time — `check`/`lint`/`build`/`test` all pass, this only surfaces on an actual form POST — the moment a route has any named action alongside `default` ("When using named actions, the default action cannot be used"). Real incident: adding a `book` named action to `/contact/+page.server.ts` (which already had a bare `default` action for the contact form) broke `/contact`'s own contact form immediately, discovered only by submitting it. The fix is to name every action once a route needs more than one (`contact`/`book` here, not `default`/`book`) and point each `<form>` at its own action explicitly (`action="?/contact"`) — a form with no `action` attribute posts to `default`, which no longer exists once every action is named.
- **`@sveltejs/adapter-cloudflare`** — deploys as a Cloudflare Worker. `wrangler.jsonc` is the deployment config; `worker-configuration.d.ts` (generated by `bun run gen`) types `platform.env`.
- **Tailwind v4** via `@tailwindcss/vite` — CSS-first config, no `tailwind.config.js`. Theme values (colors, fonts, etc.) are registered with an `@theme` block in `src/lib/styles/tokens.css`, not in JS. `@tailwindcss/forms` and `@tailwindcss/typography` plugins are enabled in `src/routes/layout.css`.
- **TypeScript** — `strict: true` in `tsconfig.json`. Never weaken this. Prefer discriminated unions over optional-field soup when a value has real variants. `tsconfig.json` declares its own `include` (mirroring SvelteKit's generated one, plus `scripts/**/*.ts`) so standalone scripts under `scripts/` are typechecked by `bun run check` too, not just `src/`. If `svelte-kit sync` ever changes what SvelteKit's own generated include list contains, re-sync this list by hand.
- **ESLint + Prettier** — `eslint.config.js` / `prettier.config.js`. Run `bun run lint` before considering any change done; `bun run format` to auto-fix.
- **Accessibility linting lives in `svelte-check`, not ESLint.** Verified directly (`eslint-plugin-svelte@3.23.0`'s rule registry has zero `a11y-*` rules, checked programmatically — this isn't a config gap, the plugin doesn't ship them at all in this major version): the Svelte compiler itself emits `a11y_*` warnings (missing `alt`, missing keyboard handler on a clickable `<div>`, missing ARIA role, etc.) directly, surfaced through `svelte-check` — i.e. through `bun run check`, already in CI. Don't go looking for an `eslint-plugin-jsx-a11y`-style config to add; there's nothing missing.
- **bun** — the package manager and script runner for this repo. Don't introduce npm/pnpm/yarn lockfiles.
- **zod** (added 2026-09-10, for `calBooking.ts`'s `bookingInputSchema`) — the one schema-validation library in this codebase. Every other form (`/contact`'s own `default` action, `/newsletter`) still hand-validates flat string fields inline, which is simpler and remains the right call for that shape; zod earned its place specifically for the booking form's nested/enum-like input (attendee object, a fixed 15/30/45/60 duration union, a location union with a conditionally-required phone field) where hand-rolled `if` chains would be more error-prone than a schema. Don't reach for zod on a new flat form without a similar complexity justification — that's exactly the "second way to do the same job" the native-first policy warns against.
- **Vitest + `vitest-browser-svelte`** (added via `bun x sv add vitest="usages:unit,component" --no-git-check --install bun`, the Svelte CLI's own add-on — not hand-configured) — component tests run in real headless Chromium via `@vitest/browser-playwright`, not jsdom; this is the current SvelteKit-recommended approach for testing Svelte 5 runes-based components reliably. Two Vitest "projects" are configured in `vite.config.ts`: `client` (`src/**/*.svelte.{test,spec}.ts`, browser-mode) for component tests, `server` (`src/**/*.{test,spec}.ts` plus `scripts/**/*.{test,spec}.ts`, excluding the `.svelte.*` ones, Node environment) for plain logic tests — the latter also covers `scripts/lib/`'s pure content-sync helpers, since they're just as testable as `src/lib/utils/` even though nothing under `scripts/` ships in the deployed app. A component test lives next to its component as `Thing.svelte.spec.ts`.

## Scripts (`package.json`)

- `bun run dev` — local dev server.
- `bun run build` — removes stale build artifacts, typechecks wrangler bindings, then builds for Cloudflare.
- `bun run preview` — runs the built Worker locally via wrangler.
- `bun run check` — cleans build artifacts + wrangler types + `svelte-kit sync` + `svelte-check`. Run this after any non-trivial change.
- `bun run lint` / `bun run format` — Prettier + ESLint.
- `bun run gen` — regenerates `worker-configuration.d.ts` from `wrangler.jsonc` (run after changing bindings/vars in `wrangler.jsonc`).
- `bun run test` — runs the full Vitest suite once (`--run`, no watch) across both projects. `bun run test:unit` runs Vitest in watch mode.

**Gotcha:** `wrangler types` embeds a self-referencing type import of the compiled worker (`mainModule: typeof import("./.svelte-kit/cloudflare/_worker")`) whenever `.svelte-kit/cloudflare/_worker.js` exists, so the generated file — and whether `wrangler types --check` passes — depends on whether a previous build left its output behind. It also makes `bun run check` fail with hundreds of unrelated implicit-`any` errors from the built output itself. `build`, `check`, and `gen` therefore run `scripts/clean-build-artifacts.ts` first, which deletes `.svelte-kit/cloudflare`, `.svelte-kit/cloudflare-tmp`, and `.svelte-kit/output` (with retries for transient Windows file locks), keeping the committed `worker-configuration.d.ts` always the no-`mainModule` variant. The clean step can fail with `EPERM`/`EBUSY` if `bun run preview` is running — stop it first. **`bun run dev` can cause the exact same lock too** (discovered 2026-09-09, not just `preview` as previously documented here): `@sveltejs/adapter-cloudflare`'s dev-mode Cloudflare runtime emulation spawns its own `workerd.exe` child process under `vite dev` to accurately emulate `platform.env`/bindings locally, and that child can hold a handle on `.svelte-kit/cloudflare` the same way `wrangler dev`/`preview`'s does. If `check`/`build`/`gen` fails with this lock and no `preview` process is running, check for a `workerd.exe` process too (Windows: `Get-CimInstance Win32_Process -Filter "Name='workerd.exe'"` shows its parent PID, which traces back to whichever `dev`/`preview` session spawned it) — **don't kill it without checking whose session it belongs to first**, since it's very plausibly a live dev server someone (the user, not just Claude) is actively using, not an orphaned leftover. If it can't be safely stopped, running the quality gate is reasonable to defer to CI (a clean runner has none of this) rather than force-killing another session's process. If you run `wrangler types` by hand instead of via `bun run gen`, delete those directories yourself before it, or you'll reintroduce the bad state.

## CI and deploy

`.github/workflows/ci.yml` runs on every push and pull request: `check` → `lint` → `build` → `test`, as separate steps so a failure is legible at a glance. `build` runs in CI (not just `check`) deliberately — it's the only command that actually prerenders every route and catches build-time-only failures (e.g. adapter-cloudflare's requirement that `_headers` live at the repo root, not `static/`) that `check`/`lint`/`test` can't see.

`.github/workflows/deploy.yml` (added 2026-09-09) runs `bun run build` + `wrangler deploy` (via `cloudflare/wrangler-action`) whenever `ci.yml` finishes successfully on `main` (`workflow_run`, not a second `push` trigger — this is what guarantees a deploy never ships code that failed the quality gate). **This closed a real, previously-unnoticed gap:** every deploy before this workflow existed was a manual `wrangler deploy` run from someone's local machine — nothing in CI ever shipped a change to the live site automatically. That silently broke the whole point of `content-sync.yml`: it committed fresh blog/video content to `main` every ~48h, but with no auto-deploy, the live site kept serving whatever was last manually deployed, sometimes days stale, until someone happened to deploy again for an unrelated reason. If `/writing` (or anything else) ever looks stale despite `posts.generated.json` being current on `main`, check whether `deploy.yml` actually ran and succeeded (Actions tab) before assuming the content sync itself is broken — the two are independent, and a green content-sync run says nothing about whether that content ever reached kamal.sh.

**Requires `CLOUDFLARE_API_TOKEN` as a GitHub Actions repository secret** (Settings → Secrets and variables → Actions) — a token created in the Cloudflare dashboard using the official **"Edit Cloudflare Workers"** template (the one Cloudflare's own CI/CD docs recommend for exactly this). Without that secret, `deploy.yml` runs and fails at the deploy step every time `ci.yml` succeeds on `main` — a human needs to add it once; nothing else about this workflow can be made to work around its absence.

**`deploy.yml` needs the same `cp .dev.vars.example .dev.vars` step `ci.yml` has, and for the identical reason** (see the `wrangler types` gotcha below) — its own `bun run build` also runs `wrangler types --check` under the hood, which infers a narrower `Env` interface with no local `.dev.vars` present, mismatching the committed `worker-configuration.d.ts` and failing the build. This bit a real deploy run (2026-09-17): the exact same `bun run build` command passed inside `ci.yml` and failed inside `deploy.yml` on the identical commit, because only one of the two workflows had the copy step. If any future workflow runs `bun run build`/`check`/`gen`, it needs this step too — don't assume it's implied by installing dependencies.

`content-sync.yml` is a separate, unrelated scheduled workflow (pulls the blog/YouTube RSS feeds every ~48h — see `scripts/sync-blog.ts`/`scripts/sync-youtube.ts`) — it doesn't run the quality gate itself, but its commits now flow through `ci.yml` → `deploy.yml` like any other push to `main`.

## `_headers` and the CSP sync guard

`_headers` (Cloudflare's native static-asset header mechanism) must live at the **repo root**, not `static/` — `@sveltejs/adapter-cloudflare` v7 errors at build time if it finds one in `static/`, a real error only `bun run build` catches (see the CI note above). It carries the same security headers as `src/hooks.server.ts`'s `handle` hook, because adapter-cloudflare's generated worker serves every prerendered page straight from `env.ASSETS.fetch()`, bypassing `handle` entirely — prerendered pages get their headers from `_headers`, the handful of genuinely SSR'd routes get them from the hook. The two Content-Security-Policy values must stay identical by hand; `src/hooks.server.spec.ts` is the automated guard that fails CI the moment they drift, rather than relying on someone noticing.

## Environment variables / secrets

- Local dev: put secrets in `.env` (gitignored) or a wrangler `.dev.vars` file if a feature needs `platform.env` access during `wrangler dev`.
- Production: set via `wrangler secret put <NAME>` (never commit secrets), read at runtime through `platform.env.<NAME>` in server-only code (`+page.server.ts`, `+server.ts`).
- `.env.example` / `.dev.vars.example` document every var a fresh clone needs, without real values.
- Non-secret config (`MAILJET_LIST_ID`, `TURNSTILE_SITE_KEY`, `CF_ACCOUNT_ID`) lives directly in `wrangler.jsonc`'s `vars` — committed, since none of the three are credentials (an identifier, a public site key, an account ID visible in any dashboard URL). `wrangler types` picks up `vars` automatically; for `.dev.vars`-only keys (real secrets) it also generates a type as long as the key exists in a local `.dev.vars` file, even with an empty value.
- **After setting up any new secret via the Cloudflare dashboard, verify its exact name with `wrangler secret list` against what the code actually reads (`grep -rn "env\.YOUR_VAR_NAME" src/`) before considering the feature done.** A name mismatch is not an error anywhere — `env.YOUR_VAR_NAME` just silently resolves to `undefined`, the code takes its documented fail-closed path, and the feature looks "not configured yet" indefinitely with zero signal pointing at the real cause. This happened for real: `TURNSTILE_SECRET_KEY` was once set in the Cloudflare dashboard under the name `TURNSTILE_SITE_SECRET`, and both `/contact` and `/newsletter` silently rejected every real submission until `wrangler secret list` was checked directly against the code. Don't assume "the user said they added it in the dashboard" means the name matches what the code reads — check.

**Mailjet (contact form email + `/newsletter` mailing list) — fully configured, live in production:**

- Domain: `mail.kamal.sh` (a dedicated sending subdomain, chosen over `m.kamal.sh` — a fuller word reads better in SPF/DKIM records and sender addresses).
- `MAILJET_KEY`, `MAILJET_SECRET`, `MAILJET_DOMAIN` are secrets (`wrangler secret put`, or the Cloudflare dashboard); `MAILJET_LIST_ID` (the `/newsletter` contact list's numeric ID — not a credential) is a plain `vars` entry. All four are set. If any is ever unset, the corresponding form fails closed with a clear "not configured yet" error rather than silently failing — see `src/routes/contact/+page.server.ts` / `src/routes/newsletter/+page.server.ts`.
- `src/lib/server/mailjet.ts` / `src/lib/server/mailjetList.ts` call Mailjet's Send API v3.1 / Contact Lists API directly via `fetch` (no SDK dependency, per the native-first policy below).

**Turnstile (bot protection on `/contact` + `/newsletter`) — fully configured, live in production:**

- `TURNSTILE_SITE_KEY` (public, embedded in page HTML — a plain `vars` entry) and `TURNSTILE_SECRET_KEY` (a real secret, server-side-only) are both set. See the callout above the Mailjet section — this exact secret had a real name-mismatch incident; if Turnstile ever appears to stop working, `wrangler secret list` is the first thing to check, before assuming the widget itself broke.
- `NewsletterSubscribeForm.svelte` needs its site key at build time, not request time, because it's also embedded on `/writing`, which stays prerendered — see `src/lib/utils/turnstileSiteKey.ts` and architecture.md's "Form abuse protection" for why this one value is read two different ways depending on the caller.

**Cloudflare Analytics (`/status` — live request/error counts) — partially configured:**

- `CF_ACCOUNT_ID` is set (a plain `vars` entry — not a secret, visible in any Cloudflare dashboard URL). `CF_API_TOKEN` (a real secret, scoped to **Account Analytics: Read** only) is **not** set yet — outstanding step: create that token in the Cloudflare dashboard, then `wrangler secret put CF_API_TOKEN` for production plus a local `.dev.vars` value for testing.
- Until `CF_API_TOKEN` is set, `/status` shows an honest "not configured yet" state rather than a fabricated number — see `src/routes/status/+page.server.ts` and `src/lib/server/cloudflareAnalytics.ts`.

**Cal.com API (`/contact`'s booking flow) — added 2026-09-10, needs the real key set:**

- `CAL_API_KEY` (a real secret — a Cal.com personal API key from Settings → Security, `cal_live_...`) is the only credential this needs. Not yet set at the time this was added — `wrangler secret put CAL_API_KEY` for production plus a real value in local `.dev.vars` for testing (placeholder empty entries already added to both `.dev.vars.example` and `.dev.vars`).
- Until it's set, the booking form's `?/book` action fails closed with the same "not configured yet" pattern as Mailjet/Turnstile — see `src/routes/contact/+page.server.ts` and `src/lib/server/calBooking.ts`.
- Unlike Mailjet/Turnstile, this key was never entered by Claude directly, even when the user pasted the raw value into chat — API keys/secrets are never something an agent should type into a file or command on the user's behalf, regardless of who supplies the value or how directly they ask. The user sets this one themselves, the same way as every other secret in this project.

## Adding a dependency — checklist

Before running `bun add`:

1. Can Svelte 5 runes or a browser API (native `<dialog>`, `IntersectionObserver`, `ResizeObserver`, View Transitions, etc.) do this with no dependency?
2. Is there a SvelteKit-official or Svelte-core-team package for it?
3. Only if both are "no": pick the single most reliable, actively-maintained option in its category. Don't add a second library that overlaps an existing one.

Every dependency in `package.json` should be traceable to a real, current need. If you remove the last usage of a package, remove the package.
